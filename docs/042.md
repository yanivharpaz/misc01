Thought for 1m 46s

Mostly no, not by itself.

ALTER TABLE xx NOLOGGING only changes the table’s logging attribute. It does not make normal inserts/updates/deletes stop generating redo.

The key rule is:

alter table xx nologging;

helps only when the load uses a direct-path operation, for example:

insert /*+ append */ into xx
select ...
from source_table;

commit;

Oracle’s docs say that with NOLOGGING, conventional inserts are still logged, while direct-path inserts are not logged for the data portion, assuming the database or tablespace is not in FORCE LOGGING.

So for a staging table:

alter table stg_x nologging;

truncate table stg_x;

insert /*+ append */ into stg_x
select ...
from ...;

commit;

That is the usual pattern if the staging data is disposable/reloadable.

Important caveats:

Regular inserts still generate redo

This:

insert into stg_x values (...);

or a normal application/JDBC batch insert will still generate normal redo. Oracle documents that conventional INSERT always generates redo and undo for data and metadata, regardless of the table’s logging setting.

UPDATE and DELETE still generate redo

NOLOGGING is mainly useful for bulk load-style operations, not ongoing row-by-row DML.

FORCE LOGGING overrides it

If the database or tablespace is in FORCE LOGGING, Oracle ignores the table’s NOLOGGING setting. This is common in Data Guard / standby environments.

Check:

select force_logging from v$database;

select tablespace_name, force_logging
from dba_tablespaces
where tablespace_name = 'YOUR_TABLESPACE';

It still produces some redo

Even with direct-path INSERT into a NOLOGGING table, Oracle still writes redo for metadata/dictionary changes and extent invalidation. So it is “minimal redo,” not literally zero redo.

Indexes can still be a big redo source

If the staging table has indexes, maintaining them during load can generate redo. For pure staging tables, often the fastest pattern is:

truncate table stg_x;

-- optionally drop/disable/rebuild indexes depending on your process

insert /*+ append */ into stg_x
select ...
from ...;

commit;

Recovery risk

NOLOGGING operations are not fully recoverable from redo. Oracle notes that media recovery from a backup taken before a NOLOGGING operation does not recreate the object’s data; for important objects, take a backup after the NOLOGGING load.

For a disposable staging table, NOLOGGING plus INSERT /*+ APPEND */ is usually the right idea. For normal row-by-row staging inserts, ALTER TABLE xx NOLOGGING alone will not materially reduce redo.

Best option: DBMS_LOCK

Oracle has an application-level locking package designed exactly for this kind of “only one process may run this section” problem. DBMS_LOCK lets sessions request a named lock, use exclusive mode, choose a zero-second timeout, and hold the lock until explicitly released or until the DB session ends. Oracle documents this package as a way to synchronize applications and enforce sequential processing, and REQUEST supports timeout and release_on_commit; if release_on_commit is false, the lock is held until release or session end.

Python pattern

Use a separate Oracle connection just for the lock. Keep it open while the ETL runs.

import sys
import traceback
import oracledb

LOCK_NAME = "ETL_HADOOP_TO_ORACLE_STG_FINAL"


def acquire_dbms_lock(conn, lock_name: str) -> str | None:
    """
    Returns the DBMS_LOCK handle if acquired.
    Returns None if another process already owns the lock.
    Raises for unexpected DB errors.
    """
    cur = conn.cursor()

    result = cur.var(oracledb.NUMBER)
    lock_handle = cur.var(oracledb.STRING, size=128)

    cur.execute(
        """
        declare
            l_handle varchar2(128);
        begin
            dbms_lock.allocate_unique(
                lockname   => :lock_name,
                lockhandle => l_handle
            );

            :result := dbms_lock.request(
                lockhandle        => l_handle,
                lockmode          => dbms_lock.x_mode,
                timeout           => 0,
                release_on_commit => false
            );

            :lock_handle := l_handle;
        end;
        """,
        lock_name=lock_name,
        result=result,
        lock_handle=lock_handle,
    )

    rc = int(result.getvalue())

    if rc == 0:
        return lock_handle.getvalue()

    if rc == 1:
        # Timeout. Since timeout=0, this means another pod already has the lock.
        return None

    raise RuntimeError(f"Unexpected DBMS_LOCK.REQUEST return code: {rc}")


def release_dbms_lock(conn, lock_handle: str) -> None:
    cur = conn.cursor()
    result = cur.var(oracledb.NUMBER)

    cur.execute(
        """
        begin
            :result := dbms_lock.release(:lock_handle);
        end;
        """,
        result=result,
        lock_handle=lock_handle,
    )

    rc = int(result.getvalue())

    if rc not in (0, 4):
        # 0 = success.
        # 4 = you do not own the lock; can happen if the session died/reconnected.
        raise RuntimeError(f"Unexpected DBMS_LOCK.RELEASE return code: {rc}")


def run_etl():
    # Your real ETL here:
    # 1. Pull from Hadoop
    # 2. Load staging table
    # 3. Move/merge into final table
    pass


def main():
    lock_conn = oracledb.connect(
        user="...",
        password="...",
        dsn="...",
    )

    lock_handle = None

    try:
        lock_handle = acquire_dbms_lock(lock_conn, LOCK_NAME)

            print("Another ETL pod is already running. Exiting.")

        sys.exit(1)

            finally:
                lock_conn.close()

Key details:

timeout => 0 means “do not wait.” The losing pod exits immediately.

release_on_commit => false is important because your ETL probably commits during staging/final-table processing. With false, ETL commits do not release the lock. Oracle documents that otherwise the lock can be released on commit/rollback, while with false it is held until explicit release or session end.

Use a separate lock_conn. Oracle documents that DBMS_LOCK.ALLOCATE_UNIQUE performs a commit, so you do not want to call it on a connection that has uncommitted ETL work.

If the winning pod crashes and the DB session dies, Oracle releases the user lock automatically at session termination.

Possible issue: you may not have permission to execute DBMS_LOCK. Oracle’s docs mention that EXECUTE on DBMS_LOCK should usually be granted carefully, often through a limited wrapper package. If you lack the privilege, ask the DBA for either:

grant execute on dbms_lock to your_schema;

or, better, a small approved wrapper package that exposes only try_acquire_etl_lock and release_etl_lock.

With FOR UPDATE NOWAIT, the losing pod gets ORA-00054 immediately once Oracle tries to lock the row.

+ time for Oracle to find the one lock row
+ immediate failed lock attempt
+ time to send error back to Python

Usually that is milliseconds to a few hundred milliseconds, depending on network latency, DB load, connection setup, and whether the connection already exists. It should not wait 60 seconds.
