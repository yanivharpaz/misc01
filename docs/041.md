Yes. Use `DBMS_JOB.SUBMIT` with a `SYSDATE + 3/1440` interval. In Oracle `DATE` arithmetic is in days, so `3/1440` = 3 minutes.

Below is a clean pattern.

### 1. Log table

If your table already exists, just match the column names in the later `INSERT`.

```sql
create table session_log
(
    sample_time date not null,
    username    varchar2(128),
    machine     varchar2(64),
    program     varchar2(48),
    logon_time  date
);
```

Those column sizes match the documented `V$SESSION` column definitions: `USERNAME` is `VARCHAR2(128)`, `MACHINE` is `VARCHAR2(64)`, `PROGRAM` is `VARCHAR2(48)`, and `LOGON_TIME` is a `DATE`. `V$SESSION` itself shows current session information. ([Oracle Docs][1])

### 2. Create a procedure to take one snapshot

```sql
create or replace procedure log_vsession_snapshot
as
begin
    insert into session_log
    (
        sample_time,
        username,
        machine,
        program,
        logon_time
    )
    select
        sysdate,
        username,
        machine,
        program,
        logon_time
    from v$session
    where username is not null;

    commit;
end;
/
```

The `where username is not null` skips Oracle background sessions. Remove that predicate if you want literally every row visible to you in `V$SESSION`.

### 3. Submit the DBMS_JOB

```sql
set serveroutput on

declare
    l_job number;
begin
    dbms_job.submit
    (
        job       => l_job,
        what      => 'log_vsession_snapshot;',
        next_date => sysdate,
        interval  => 'sysdate + 3/1440'
    );

    commit;

    dbms_output.put_line('Created job: ' || l_job);
end;
/
```

Oracle documents `DBMS_JOB.SUBMIT(job, what, next_date, interval, ...)`, where `what` is the PL/SQL to run and `interval` is a date expression used to calculate the next run time. Oracle also notes that the submitted job is not available to the job queue until you `COMMIT`, so the `commit` after `dbms_job.submit` is important. ([Oracle Docs][2])

### 4. Check the job

```sql
select
    job,
    last_date,
    last_sec,
    next_date,
    next_sec,
    failures,
    broken,
    what
from user_jobs
where what like '%log_vsession_snapshot%';
```

To test it immediately:

```sql
begin
    dbms_job.run(<job_number>);
end;
/
```

Then check the log:

```sql
select *
from session_log
order by sample_time desc;
```

### 5. Remove it later

```sql
begin
    dbms_job.remove(<job_number>);
    commit;
end;
/
```

### Important privilege gotchas

Even if `select * from v$session` works manually, the procedure/job can still fail if your access comes through a role instead of a direct grant. Definer-rights stored procedures run with roles disabled, so the owner needs the required object privileges directly. Oracle documents that roles are disabled in definer-rights named PL/SQL blocks. ([Oracle Docs][3])

You can test that with:

```sql
set role none;

select username, machine, program, logon_time
from v$session
where rownum = 1;
```

If that fails, ask the DBA for a direct grant, usually:

```sql
grant select on sys.v_$session to your_schema;
```

Also, on newer Oracle versions, `DBMS_JOB` is legacy and Oracle says it has been superseded by `DBMS_SCHEDULER`; Oracle also documents that `CREATE JOB` is required to use `DBMS_JOB`. ([Oracle Docs][2])

So if the submit fails, the DBA may need to grant:

```sql
grant create job to your_schema;
```

or allow you to use `DBMS_SCHEDULER` instead.
