For this workload, the fastest path is usually:

1. keep `python-oracledb` in **thin mode** unless you truly need a Thick-client feature,
2. make the SQL return only the 10k rows the chart actually needs,
3. use a **connection pool** and tune `arraysize` / `prefetchrows`,
4. cache the final chart payload in **Redis** only if many requests repeat the same data,
5. do **not** expect NGINX to speed up the Oracle query itself.

## A good Python pattern

This is a solid baseline for a high-throughput backend in a Kubernetes pod.

```python
import os
import oracledb
from datetime import datetime
from typing import Any

# Thin mode is default. Leave this out unless you need Thick mode:
# oracledb.init_oracle_client(lib_dir="/opt/oracle/instantclient")

POOL = oracledb.create_pool(
    user=os.environ["ORA_USER"],
    password=os.environ["ORA_PASSWORD"],
    dsn=os.environ["ORA_DSN"],          # e.g. "dbhost:1521/service"
    min=1,
    max=10,
    increment=1,
    getmode=oracledb.POOL_GETMODE_WAIT,
    stmtcachesize=50,
    ping_interval=60,
)

SQL = """
    SELECT
        bucket_ts,
        metric_value
    FROM chart_data_view
    WHERE bucket_ts >= :start_ts
      AND bucket_ts <  :end_ts
    ORDER BY bucket_ts
"""

def fetch_chart_data(start_ts: datetime, end_ts: datetime) -> list[dict[str, Any]]:
    conn = POOL.acquire()
    try:
        with conn.cursor() as cur:
            # Tune these for your row width and network.
            # For ~10k rows, 1000-5000 is usually a good starting range.
            cur.arraysize = 2000
            cur.prefetchrows = 2000

            cur.execute(SQL, start_ts=start_ts, end_ts=end_ts)

            rows = cur.fetchall()

        # Keep the Python-side transformation lean.
        # If your chart can consume tuples or arrays, that is even faster than dicts.
        return [
            {"x": r[0].isoformat(), "y": r[1]}
            for r in rows
        ]
    finally:
        conn.close()   # returns pooled connection
```

## What actually matters for speed

### 1) Use a pool, not a new connection per request

Opening a new Oracle session for every request is expensive. A pool keeps sessions ready.

That one change often helps more than switching thin/thick.

### 2) Tune fetch size

For Oracle fetches, these matter a lot:

* `cursor.arraysize`
* `cursor.prefetchrows`

They control how many rows are pulled per round trip.
For 10k rows, start with `1000`, `2000`, and `5000`, then benchmark.

A reasonable rule of thumb:

* small rows: larger values work well
* wide rows: too large can waste memory
* the best value depends on row width, latency, and network

### 3) Keep SQL cheap

If the chart does not need raw detail, aggregate in Oracle before Python sees it.

Example:

* chart by minute, hour, or day
* use a summary table or materialized view
* index the filter and sort columns

If the chart is showing time series data, a materialized view or precomputed summary table is often the biggest win of all.

### 4) Return a chart-friendly payload

If Angular can consume arrays directly, avoid building large nested objects in Python.

Better:

```json
[
  [1700000000000, 123.4],
  [1700000600000, 124.1]
]
```

Faster than:

```json
[
  {"timestamp":"...", "value":123.4}
]
```

That reduces Python object creation and JSON size.

### 5) Compress HTTP responses

If the payload is large, enable gzip or brotli on the API layer.
This reduces network time, especially for chart data.

## Thin mode vs Thick mode

For plain querying, **thin mode is usually enough**.

Use Thick mode only if you need a feature that thin mode does not cover in your environment, or if your Oracle/network/security setup specifically requires Oracle Client libraries.

For your use case, Thick mode is **not automatically faster**.
The performance wins usually come from pooling, fetch tuning, SQL design, and caching.

## Redis vs NGINX

### Redis

Redis helps a lot **if the same chart query is requested repeatedly** between database refreshes.

Since your data changes only once an hour or once a day, Redis can be a big win if:

* the chart is the same for many users,
* the query parameters are limited,
* the data can be cached safely with TTL or versioned invalidation.

Typical pattern:

* build a cache key from the query parameters
* look in Redis first
* on miss, query Oracle, serialize result, store in Redis
* expire the key a little before the next expected refresh

Example:

```python
import json
import redis

r = redis.Redis(host=os.environ["REDIS_HOST"], port=6379, decode_responses=True)

def get_chart_data_cached(start_ts, end_ts):
    cache_key = f"chart:{start_ts.isoformat()}:{end_ts.isoformat()}"
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)

    data = fetch_chart_data(start_ts, end_ts)
    r.setex(cache_key, 3600, json.dumps(data))  # adjust TTL to your refresh cycle
    return data
```

Redis does **not** make the Oracle query faster.
It makes repeated requests avoid Oracle entirely.

If you have many users looking at the same chart, Redis can reduce latency dramatically.
If every request is unique, the gain is much smaller.

### NGINX

NGINX is useful for:

* TLS termination
* HTTP keep-alive
* gzip/brotli compression
* caching HTTP responses
* serving static files

It does **not** speed up the database query itself.

So:

* for query speed: NGINX = almost no help
* for network delivery and API overhead: NGINX can help a bit
* for repeated identical chart responses: NGINX cache can help, but Redis is usually the more flexible cache

5. If the same chart data is reused across requests, add **Redis** caching.

## 1. Production-style sync implementation: Thin or Thick

This version works in **Thin mode** by default and in **Thick mode** when `ORACLE_THICK=1`. It is written as a FastAPI example, but the database layer can be used from any Python backend.

`requirements.txt`

```text
oracledb
fastapi
uvicorn[standard]
orjson
```

`app.py`

```python
import base64
import datetime as dt
import decimal
import os
import time
from contextlib import asynccontextmanager
from typing import Any

import oracledb
import orjson
from fastapi import FastAPI, HTTPException, Query, Response


POOL: oracledb.ConnectionPool | None = None


def env_int(name: str, default: int) -> int:
    raw = os.getenv(name)
    if raw is None or raw == "":
        return default
    try:
        return int(raw)
    except ValueError as exc:
        raise RuntimeError(f"{name} must be an integer, got {raw!r}") from exc


def init_oracle_driver() -> None:
    """
    Must run before creating any standalone connection or pool.

    Thin mode:
      - default
      - no Oracle Client libraries

    Thick mode:
      - set ORACLE_THICK=1
      - Oracle Instant Client must be installed in the image
      - on Linux, the client library directory should be in ldconfig /
        system loader path before Python starts
    """
    use_thick = os.getenv("ORACLE_THICK", "0").lower() in {"1", "true", "yes"}

    if use_thick:
        config_dir = os.getenv("ORACLE_CONFIG_DIR")
        if config_dir:
            oracledb.init_oracle_client(config_dir=config_dir)
        else:
            oracledb.init_oracle_client()

    # Application-wide defaults. Hot queries below override per cursor.
    oracledb.defaults.arraysize = env_int("ORACLE_DEFAULT_ARRAYSIZE", 1000)
    oracledb.defaults.prefetchrows = env_int("ORACLE_DEFAULT_PREFETCHROWS", 1000)
    oracledb.defaults.stmtcachesize = env_int("ORACLE_STMT_CACHE_SIZE", 100)


def create_db_pool() -> oracledb.ConnectionPool:
    """
    Create one pool per Python process, at process startup.

    Important for Kubernetes:
      total possible DB sessions =
        replicas * web_server_workers_per_pod * ORACLE_POOL_SIZE
    """
    pool_size = env_int("ORACLE_POOL_SIZE", 4)

    return oracledb.create_pool(
        user=os.environ["ORACLE_USER"],
        password=os.environ["ORACLE_PASSWORD"],
        dsn=os.environ["ORACLE_DSN"],

        # Fixed-size pool: preferred for predictable DB load.
        min=pool_size,
        max=pool_size,
        increment=0,

        # Do not create unlimited extra sessions when the pool is busy.
        getmode=oracledb.POOL_GETMODE_TIMEDWAIT,
        wait_timeout=env_int("ORACLE_POOL_WAIT_TIMEOUT_MS", 3000),

        # Set close to the number of distinct SQL statements used by this app.
        stmtcachesize=env_int("ORACLE_STMT_CACHE_SIZE", 100),

        # Avoid pinging on every acquire. Positive value allows periodic checks.
        ping_interval=env_int("ORACLE_POOL_PING_INTERVAL", 60),
    )


@asynccontextmanager
async def lifespan(app: FastAPI):
    global POOL

    init_oracle_driver()
    POOL = create_db_pool()

    try:
        yield
    finally:
        if POOL is not None:
            POOL.close(force=True)
            POOL = None


app = FastAPI(lifespan=lifespan)


# Use two stable SQL statements instead of one statement with
# "(:last_id is null or id > :last_id)" so the optimizer can more easily use
# an index range scan. Adjust column names and predicates to your real schema.
SQL_FIRST_PAGE = """
select
       id,
       tenant_id,
       created_at,
       status,
       amount
from   my_schema.my_big_table
where  tenant_id = :tenant_id
and    created_at >= :from_ts
and    created_at <  :to_ts
order  by id
fetch next :limit rows only
"""

SQL_AFTER_ID = """
select
       id,
       tenant_id,
       created_at,
       status,
       amount
from   my_schema.my_big_table
where  tenant_id = :tenant_id
and    created_at >= :from_ts
and    created_at <  :to_ts
and    id > :last_id
order  by id
fetch next :limit rows only
"""


def json_default(value: Any) -> Any:
    """
    orjson handles many standard types itself. This catches common Oracle
    values that JSON cannot represent directly.
    """
    if isinstance(value, decimal.Decimal):
        # Use str to avoid precision loss. Use float(value) only if acceptable.
        return str(value)

    if isinstance(value, (dt.datetime, dt.date)):
        return value.isoformat()

    if isinstance(value, bytes):
        # RAW/BLOB data needs an explicit representation in JSON.
        return base64.b64encode(value).decode("ascii")

    raise TypeError(f"Object of type {type(value).__name__} is not JSON serializable")


def fetch_rows_fast(
    *,
    tenant_id: int,
    from_ts: dt.datetime,
    to_ts: dt.datetime,
    last_id: int | None,
    limit: int,
) -> tuple[bytes, dict[str, str]]:
    if POOL is None:
        raise RuntimeError("Oracle connection pool was not initialized")

    sql = SQL_AFTER_ID if last_id is not None else SQL_FIRST_PAGE

    params: dict[str, Any] = {
        "tenant_id": tenant_id,
        "from_ts": from_ts,
        "to_ts": to_ts,
        "limit": limit,
    }
    if last_id is not None:
        params["last_id"] = last_id

    # For 10k narrow rows, benchmark 2000, 5000, and 10000.
    # 10000 + prefetchrows=10001 can be fastest but uses more memory.
    configured_fetch_size = env_int("ORACLE_FETCH_ARRAYSIZE", 5000)
    fetch_size = max(1, min(configured_fetch_size, limit))

    t0 = time.perf_counter()

    with POOL.acquire() as conn:
        with conn.cursor() as cur:
            # Must be set before execute().
            cur.arraysize = fetch_size

            # When fetch_size == limit and rows are narrow, limit+1 can avoid
            # an extra end-of-fetch round trip. For wider rows, start lower.
            if fetch_size == limit:
                cur.prefetchrows = limit + 1
            else:
                cur.prefetchrows = fetch_size

            cur.execute(sql, params)
            t_execute = time.perf_counter()

            # Safe because API limit is <= 10k. For larger exports, stream with
            # fetchmany() instead of building one in-memory payload.
            rows = cur.fetchall()
            t_fetch = time.perf_counter()

            # Return arrays, not list[dict]. This avoids creating 10k dicts and
            # repeating column names for every row in JSON.
            columns = [col.name.lower() for col in cur.description]

    payload = {
        "columns": columns,
        "rows": rows,
        "count": len(rows),
        "has_more": len(rows) == limit,
    }

    body = orjson.dumps(payload, default=json_default)
    t_json = time.perf_counter()

    headers = {
        "Server-Timing": (
            f"db_execute;dur={(t_execute - t0) * 1000:.1f}, "
            f"db_fetch;dur={(t_fetch - t_execute) * 1000:.1f}, "
            f"json;dur={(t_json - t_fetch) * 1000:.1f}"
        ),
        "X-Row-Count": str(len(rows)),
    }

    return body, headers


@app.get("/rows")
def get_rows(
    tenant_id: int,
    from_ts: dt.datetime,
    to_ts: dt.datetime,
    last_id: int | None = None,
    limit: int = Query(default=10_000, ge=1, le=10_000),
) -> Response:
    try:
        body, headers = fetch_rows_fast(
            tenant_id=tenant_id,
            from_ts=from_ts,
            to_ts=to_ts,
            last_id=last_id,
            limit=limit,
        )
    except oracledb.Error as exc:
        raise HTTPException(status_code=503, detail=str(exc)) from exc

    return Response(
        content=body,
        media_type="application/json",
        headers=headers,
    )


@app.get("/health")
def health() -> dict[str, Any]:
    if POOL is None:
        raise HTTPException(status_code=503, detail="pool not initialized")

    with POOL.acquire() as conn:
        db_version = conn.version
        thin = conn.thin

    return {
        "ok": True,
        "oracle_thin_mode": thin,
        "db_version": db_version,
        "pool_opened": POOL.opened,
        "pool_busy": POOL.busy,
    }
```

Why this shape is fast:

The pool is created once during application startup; Oracle’s docs recommend connection pooling for multi-user applications and creating the pool at initialization, not per request. They also note that connection pools must be created, used, and closed within the same process, which matters when you use multiple Uvicorn/Gunicorn workers. ([Python OracleDB][2])

The pool is fixed-size with `min == max`. Oracle’s Real-World Performance guidance, reflected in the python-oracledb docs, recommends fixed-size pools to avoid connection storms and keep DB load predictable. Keep the pool small and scale by measurement; in Kubernetes, the real session ceiling is `replicas * workers_per_pod * pool_size`. ([Python OracleDB][1])

For fetch performance, `arraysize` and `prefetchrows` should be set before `execute()`. Oracle’s docs show that increasing `arraysize` reduces round trips; for 10,000 rows, their table shows default-style `arraysize=100` needs many more round trips than `arraysize=1000`, and for fixed row counts the recommended pattern is `arraysize = expected_rows`, `prefetchrows = expected_rows + 1`, subject to memory tradeoffs. ([Python OracleDB][2])

The endpoint returns `{columns, rows}` instead of a list of dictionaries. For 10k rows, this avoids building 10k Python dicts and avoids repeating column names in every JSON row. That is not an Oracle feature; it is just reducing Python and JSON payload overhead.

## 2. Async Thin-mode variant

Use this when your service is truly async and you want to avoid a threadpool. The python-oracledb async API is **Thin-mode only**, so do not call `oracledb.init_oracle_client()` in this version. ([Python OracleDB][3])

```python
import datetime as dt
import os
from contextlib import asynccontextmanager
from typing import Any

import oracledb
import orjson
from fastapi import FastAPI, HTTPException, Query, Response


ASYNC_POOL: oracledb.AsyncConnectionPool | None = None


def env_int(name: str, default: int) -> int:
    raw = os.getenv(name)
    return default if raw in (None, "") else int(raw)


SQL_FIRST_PAGE = """
select id, tenant_id, created_at, status, amount
from   my_schema.my_big_table
where  tenant_id = :tenant_id
and    created_at >= :from_ts
and    created_at <  :to_ts
order  by id
fetch next :limit rows only
"""


@asynccontextmanager
async def lifespan(app: FastAPI):
    global ASYNC_POOL

    pool_size = env_int("ORACLE_POOL_SIZE", 4)

    # create_pool_async() itself is not awaited; acquire/execute/fetch are.
    ASYNC_POOL = oracledb.create_pool_async(
        user=os.environ["ORACLE_USER"],
        password=os.environ["ORACLE_PASSWORD"],
        dsn=os.environ["ORACLE_DSN"],
        min=pool_size,
        max=pool_size,
        increment=0,
        getmode=oracledb.POOL_GETMODE_TIMEDWAIT,
        wait_timeout=env_int("ORACLE_POOL_WAIT_TIMEOUT_MS", 3000),
        stmtcachesize=env_int("ORACLE_STMT_CACHE_SIZE", 100),
    )

    try:
        yield
    finally:
        if ASYNC_POOL is not None:
            await ASYNC_POOL.close(force=True)
            ASYNC_POOL = None


app = FastAPI(lifespan=lifespan)


@app.get("/rows-async")
async def get_rows_async(
    tenant_id: int,
    from_ts: dt.datetime,
    to_ts: dt.datetime,
    limit: int = Query(default=10_000, ge=1, le=10_000),
) -> Response:
    if ASYNC_POOL is None:
        raise HTTPException(status_code=503, detail="pool not initialized")

    fetch_size = min(env_int("ORACLE_FETCH_ARRAYSIZE", 5000), limit)

    params: dict[str, Any] = {
        "tenant_id": tenant_id,
        "from_ts": from_ts,
        "to_ts": to_ts,
        "limit": limit,
    }

    try:
        async with ASYNC_POOL.acquire() as conn:
            with conn.cursor() as cur:
                cur.arraysize = fetch_size
                cur.prefetchrows = limit + 1 if fetch_size == limit else fetch_size

                await cur.execute(SQL_FIRST_PAGE, params)
                rows = await cur.fetchall()
                columns = [col.name.lower() for col in cur.description]

    except oracledb.Error as exc:
        raise HTTPException(status_code=503, detail=str(exc)) from exc

    return Response(
        content=orjson.dumps(
            {
                "columns": columns,
                "rows": rows,
                "count": len(rows),
                "has_more": len(rows) == limit,
            }
        ),
        media_type="application/json",
    )
```

Use the sync version for Thick mode. Use the async version for Thin mode when request concurrency is high and you want each request to await Oracle network I/O directly.

## 4. Thick-mode Dockerfile with Oracle Instant Client

Oracle Instant Client is the usual container choice for Thick mode. Oracle describes Instant Client as free, lightweight libraries/tools for applications connecting to Oracle Database, and python-oracledb Thick mode uses Oracle Client libraries loaded by `init_oracle_client()`. ([Oracle][4])

For a 19c database, Oracle’s python-oracledb installation docs say Instant Client 23 can connect to Oracle Database 19 or later, and Instant Client 19 can connect to Oracle Database 11.2 or later. Use the version your organization standardizes on, and keep it patched. ([Python OracleDB][5])

Preparation:

1. Download the Linux Instant Client **Basic** or **Basic Light** ZIP matching your container architecture.
2. Put the ZIP next to the Dockerfile, or pull it from your internal artifact repository during the build.
3. For x86_64 use an x64 ZIP; for ARM nodes use the aarch64 ZIP.
4. Mount `tnsnames.ora`, `sqlnet.ora`, wallet files, or `oraaccess.xml` only if you need them.

```dockerfile
 && unzip -q /tmp/instantclient-basic*.zip -d /opt/oracle \
 && rm -f /tmp/instantclient-basic*.zip \
 && IC_DIR="$(find /opt/oracle -maxdepth 1 -type d -name 'instantclient_*' | head -n 1)" \

COPY requirements.txt .

# Optional: set when you mount tnsnames.ora/sqlnet.ora/wallet/oraaccess.xml.
```

## 6. Arraysize benchmark for your exact 10k-row query

Run this inside the same container/pod network path as production. The “best” value depends on row width, latency, CPU, JSON cost, and memory.

```python
import os
import time

import oracledb


SQL = """
select id, tenant_id, created_at, status, amount
from   my_schema.my_big_table
where  tenant_id = :tenant_id
and    created_at >= :from_ts
and    created_at <  :to_ts
order  by id
fetch next :limit rows only
"""


def main() -> None:
    if os.getenv("ORACLE_THICK") == "1":
        oracledb.init_oracle_client()

    pool = oracledb.create_pool(
        user=os.environ["ORACLE_USER"],
        password=os.environ["ORACLE_PASSWORD"],
        dsn=os.environ["ORACLE_DSN"],
        min=1,
        max=1,
        increment=0,
        stmtcachesize=100,
    )

    params = {
        "tenant_id": int(os.environ["BENCH_TENANT_ID"]),
        "from_ts": os.environ["BENCH_FROM_TS"],
        "to_ts": os.environ["BENCH_TO_TS"],
        "limit": 10_000,
    }

    for arraysize in (100, 500, 1000, 2000, 5000, 10000):
        elapsed_values = []

        for _ in range(5):
            with pool.acquire() as conn:
                with conn.cursor() as cur:
                    cur.arraysize = arraysize
                    cur.prefetchrows = 10001 if arraysize == 10000 else arraysize

                    t0 = time.perf_counter()
                    cur.execute(SQL, params)
                    rows = cur.fetchall()
                    elapsed_ms = (time.perf_counter() - t0) * 1000
                    elapsed_values.append(elapsed_ms)

        print(
            f"arraysize={arraysize:5d} "
            f"rows={len(rows):5d} "
            f"best_ms={min(elapsed_values):8.1f} "
            f"avg_ms={sum(elapsed_values) / len(elapsed_values):8.1f}"
        )

    pool.close()


if __name__ == "__main__":
    main()
```

Start with `ORACLE_FETCH_ARRAYSIZE=5000`. For narrow rows and moderate memory, `10000` with `prefetchrows=10001` may win. For wider rows, `2000` or `5000` may be better because it reduces memory pressure and copying.

## 7. Extra tuning notes for your case

Use bind variables for every user-supplied value. String concatenation is both a security risk and a performance problem because it can cause reparsing. ([Python OracleDB][6])

Avoid `select *`. Select only the columns the API actually returns. Oracle’s tuning guide for python-oracledb explicitly calls out limiting rows and avoiding unused columns as simple optimizations. ([Python OracleDB][2])

Make sure the query has an index that matches the filter and order. For the sample query, a likely starting index is something like `(tenant_id, created_at, id)` or `(tenant_id, id)` depending on selectivity and the real predicates. The 30M-row table size matters much less than whether the database can reach the 10k rows through a selective range scan.

Use keyset pagination where possible. For deep pages over a 30M-row table, `OFFSET` can become expensive because skipped rows still require work. A stable `id > :last_id` or `(created_at, id)` seek pattern is usually better for API pagination.

Set `stmtcachesize` near the number of distinct hot SQL statements. python-oracledb uses statement caching for efficient re-execution and to avoid reparsing/metadata overhead; the default cache size is 20, and it can be set on the pool. ([Python OracleDB][2])

Keep LOBs out of the 10k-row hot query when possible. Queries returning LOB objects do not use row prefetching, and LOB streaming adds round trips. When you must fetch CLOB/BLOB values and they fit in memory, `fetch_lobs=False` can return strings/bytes directly and may be much faster, but it increases memory usage. ([Python OracleDB][2])

Do not assume Thick mode is faster. Thick mode can be necessary for some Oracle Net features, but python-oracledb docs also note that Thick-mode prefetching can use an extra buffer and data copy, so the benefit depends on the workload. Benchmark Thin and Thick with the exact pod image, network, query, and JSON response shape. ([Python OracleDB][2])

When network throughput or latency is the bottleneck, test SDU tuning after the Python-level fetch tuning. python-oracledb docs mention SDU/socket buffer tuning for large row retrievals or slow networks; in Thick mode SDU is configured through Oracle Net files, while in Thin mode it can be passed as a connection/pool parameter or in the connect descriptor. ([Python OracleDB][2])

## Recommended response shape for a chart

Avoid this shape for 10k chart points:

```json
[
  {"ts": 1710000000000, "metricA": 12.4, "metricB": 18.9},
  {"ts": 1710000060000, "metricA": 12.7, "metricB": 19.1}
]
```

It repeats field names thousands of times and creates many JavaScript objects.

Prefer one of these.

### Option A: columnar payload

Good for Chart.js, ngx-charts, ApexCharts, and many Angular wrappers:

```json
{
  "x": [1710000000000, 1710000060000],
  "series": [
    {"name": "metricA", "data": [12.4, 12.7]},
    {"name": "metricB", "data": [18.9, 19.1]}
  ],
  "count": 2
}
```

### Option B: ECharts-style 2D table

Good if you use Apache ECharts, because ECharts has a `dataset` concept designed for shared chart data and supports 2D array data sources. ECharts documentation recommends `dataset` for separating data from chart configuration and reusing the same data across series. ([Apache ECharts][1])

```json
{
  "dimensions": ["ts", "metricA", "metricB"],
  "source": [
    [1710000000000, 12.4, 18.9],
    [1710000060000, 12.7, 19.1]
  ],
  "count": 2
}
```

For backend speed and payload size, both are much better than `list[dict]`.

## Fast Python backend example for a chart endpoint

This example uses:

* one Oracle pool per process;
* Thin mode by default;
* optional Thick mode;
* `arraysize = limit`;
* `prefetchrows = limit + 1`;
* compact chart JSON;
* `orjson`;
* gzip compression.

Oracle’s python-oracledb docs say `arraysize` and `prefetchrows` control internal fetch buffers, larger values reduce database round trips when fetching many rows, and both should be set before `execute()`. For a known fixed number of rows, the docs recommend setting `arraysize` to the expected row count and `prefetchrows` to one greater than that to avoid an extra end-of-fetch round trip. ([Python OracleDB][2])

### `requirements.txt`

```text
oracledb
fastapi
uvicorn[standard]
orjson
```

### `app.py`

```python
import datetime as dt
import os
import time
from contextlib import asynccontextmanager
from typing import Any, Literal

import oracledb
import orjson
from fastapi import FastAPI, HTTPException, Query, Response
from starlette.middleware.gzip import GZipMiddleware


POOL: oracledb.ConnectionPool | None = None


def env_int(name: str, default: int) -> int:
    raw = os.getenv(name)
    return default if raw in (None, "") else int(raw)


def init_oracle_driver() -> None:
    """
    Thin mode is default.

    Set ORACLE_THICK=1 only if you need Thick-mode features or your benchmark
    proves it is better for this workload.
    """
    use_thick = os.getenv("ORACLE_THICK", "0").lower() in {"1", "true", "yes"}

    if use_thick:
        config_dir = os.getenv("ORACLE_CONFIG_DIR")
        if config_dir:
            oracledb.init_oracle_client(config_dir=config_dir)
        else:
            oracledb.init_oracle_client()

    oracledb.defaults.arraysize = env_int("ORACLE_DEFAULT_ARRAYSIZE", 1000)
    oracledb.defaults.prefetchrows = env_int("ORACLE_DEFAULT_PREFETCHROWS", 1000)
    oracledb.defaults.stmtcachesize = env_int("ORACLE_STMT_CACHE_SIZE", 100)


def create_pool() -> oracledb.ConnectionPool:
    pool_size = env_int("ORACLE_POOL_SIZE", 4)

    return oracledb.create_pool(
        user=os.environ["ORACLE_USER"],
        password=os.environ["ORACLE_PASSWORD"],
        dsn=os.environ["ORACLE_DSN"],
        min=pool_size,
        max=pool_size,
        increment=0,
        getmode=oracledb.POOL_GETMODE_TIMEDWAIT,
        wait_timeout=env_int("ORACLE_POOL_WAIT_TIMEOUT_MS", 3000),
        stmtcachesize=env_int("ORACLE_STMT_CACHE_SIZE", 100),
        ping_interval=env_int("ORACLE_POOL_PING_INTERVAL", 60),
    )


@asynccontextmanager
async def lifespan(app: FastAPI):
    global POOL

    init_oracle_driver()
    POOL = create_pool()

    try:
        yield
    finally:
        if POOL is not None:
            POOL.close(force=True)
            POOL = None


app = FastAPI(lifespan=lifespan)

# You can also do this at ingress / nginx / envoy level.
# Starlette's GZipMiddleware compresses responses when the client sends
# Accept-Encoding: gzip; lower compresslevel is faster but compresses less.
app.add_middleware(
    GZipMiddleware,
    minimum_size=1024,
    compresslevel=4,
)
```

Starlette’s `GZipMiddleware` handles gzip responses for clients that send `Accept-Encoding: gzip`, supports `minimum_size`, and has a `compresslevel` setting from 1 to 9 where lower values are faster but produce larger output. ([Starlette][3])

## Helper conversion functions

```python
def to_epoch_ms(value: dt.datetime) -> int:
    """
    Assumption: event_ts_utc from Oracle is UTC.

    If your DB column is local time or TIMESTAMP WITH LOCAL TIME ZONE,
    normalize deliberately. Do not silently rely on the pod's local timezone.
    """
    if value.tzinfo is None:
        value = value.replace(tzinfo=dt.timezone.utc)
    else:
        value = value.astimezone(dt.timezone.utc)

    return int(value.timestamp() * 1000)


def chart_number(value: Any) -> float | int | None:
    """
    Convert Oracle numeric values into JSON chart numbers.

    Use float only if the chart does not need exact decimal precision.
    For financial/precise values, consider scaling in SQL, for example cents
    as integer, or return strings and parse intentionally in the UI.
    """
    if value is None:
        return None

    if isinstance(value, int):
        return value

    return float(value)
```

## Columnar chart endpoint

This is the shape I would start with unless your chart library strongly prefers a 2D table.

```python
@app.get("/chart-data")
def get_chart_data(
    tenant_id: int,
    from_ts: dt.datetime,
    to_ts: dt.datetime,
    limit: int = Query(default=10_000, ge=1, le=10_000),
) -> Response:
    if POOL is None:
        raise HTTPException(status_code=503, detail="Oracle pool not initialized")

    # For this chart endpoint, there is no paging.
    # Because the expected maximum is 10k rows, fetch in one large batch.
    fetch_size = limit

    params = {
        "tenant_id": tenant_id,
        "from_ts": from_ts,
        "to_ts": to_ts,
        "limit": limit,
    }

    t0 = time.perf_counter()

    x: list[int] = []
    metric_a: list[float | int | None] = []
    metric_b: list[float | int | None] = []

    try:
        with POOL.acquire() as conn:
            with conn.cursor() as cur:
                cur.arraysize = fetch_size
                cur.prefetchrows = fetch_size + 1

                cur.execute(SQL_CHART_RAW, params)
                t_execute = time.perf_counter()

                for event_ts_utc, value_a, value_b in cur:
                    x.append(to_epoch_ms(event_ts_utc))
                    metric_a.append(chart_number(value_a))
                    metric_b.append(chart_number(value_b))

                t_fetch_transform = time.perf_counter()

    except oracledb.Error as exc:
        raise HTTPException(status_code=503, detail=str(exc)) from exc

    payload = {
        "x": x,
        "series": [
            {"name": "metricA", "data": metric_a},
            {"name": "metricB", "data": metric_b},
        ],
        "count": len(x),
        "from": int(from_ts.replace(tzinfo=dt.timezone.utc).timestamp() * 1000)
        if from_ts.tzinfo is None
        else int(from_ts.astimezone(dt.timezone.utc).timestamp() * 1000),
        "to": int(to_ts.replace(tzinfo=dt.timezone.utc).timestamp() * 1000)
        if to_ts.tzinfo is None
        else int(to_ts.astimezone(dt.timezone.utc).timestamp() * 1000),
    }

    body = orjson.dumps(payload)
    t_json = time.perf_counter()

    return Response(
        content=body,
        media_type="application/json",
        headers={
            "Server-Timing": (
                f"db_execute;dur={(t_execute - t0) * 1000:.1f}, "
                f"db_fetch_transform;dur={(t_fetch_transform - t_execute) * 1000:.1f}, "
                f"json;dur={(t_json - t_fetch_transform) * 1000:.1f}"
            ),
            "X-Row-Count": str(len(x)),
        },
    )
```

This avoids building:

```python
[
    {"event_ts": ..., "metric_a": ..., "metric_b": ...},
    ...
]
```

That matters because 10k rows times several fields becomes a lot of Python dict allocations and a larger JSON payload.

## If the chart does not visually need all 10k raw points

Even though the chart uses the full dataset together, the browser may not need every raw point. If the chart is 1,200 pixels wide, sending 10,000 line points may not add visual value unless the user can zoom into them.

In that case, the fastest design is:

```text
Oracle aggregates/downsamples -> Python serializes compact chart data -> Angular renders fewer points
```

Example: return one point per time bucket.

```python
SQL_CHART_BUCKETED = """
select
       bucket_start,
       avg(metric_a) as metric_a_avg,
       avg(metric_b) as metric_b_avg,
       min(metric_a) as metric_a_min,
       max(metric_a) as metric_a_max,
       count(*)      as sample_count
from (
    select
           date '1970-01-01'
           + floor(
               ((cast(event_ts_utc as date) - date '1970-01-01') * 86400)
               / :bucket_seconds
             ) * :bucket_seconds / 86400 as bucket_start,
           metric_a,
           metric_b
    from   my_schema.my_chart_table
    where  tenant_id = :tenant_id
    and    event_ts_utc >= :from_ts
    and    event_ts_utc <  :to_ts
)
group by bucket_start
order by bucket_start
fetch next :limit rows only
"""
```

Then use a bucket size chosen by the UI width:

```text
bucket_seconds = max(1, total_range_seconds / target_point_count)
```

For example:

```text
target_point_count = 1000 to 3000
```

That often gives a chart that looks the same but loads and renders much faster.

## Important Thick-mode note for this chart case

I would **not** start with Thick mode just because the table has 30M rows. For Oracle 19c, Thin mode can connect directly without Oracle Client libraries, while Thick mode is enabled only when Oracle Client libraries are loaded. Oracle’s current python-oracledb docs say Thin mode is the default and does not need Oracle Client libraries; common Thick-mode reasons include older Oracle Database versions, Native Network Encryption/checksumming requirements, or Application Continuity/TAC. ([Python OracleDB][5])

For this exact chart workload, benchmark both only after the payload shape and `arraysize` are fixed. The docs also note that Thick-mode row prefetching uses a separate buffer and an extra data copy from the Oracle Client prefetch buffer, so prefetching is not automatically faster in Thick mode. ([Python OracleDB][2])

For Thin mode, start with:

```text
arraysize = 10000
prefetchrows = 10001
```

For Thick mode, benchmark these combinations:

```text
arraysize=10000, prefetchrows=10001
arraysize=10000, prefetchrows=2
arraysize=5000,  prefetchrows=5000
arraysize=5000,  prefetchrows=2
```

Keep the one with the best end-to-end time:

```text
DB execute + fetch + Python transform + JSON serialization + network transfer + Angular render
```

Not just the database fetch time.

```text
CPU is guaranteed at 750m for scheduling/HPA purposes
memory is protected by a hard 2Gi limit
CPU can burst when the node has spare capacity
```

This is useful because the endpoint likely has short CPU spikes during:

```text
Oracle fetch -> Python transform -> orjson serialization -> gzip/brotli
```

A CPU limit of `1` can make those spikes slower. If your organization requires CPU limits, use `2` CPU as the first limit, not `1`.

---

## Recommended pod profiles

| Profile                          | Uvicorn workers | Oracle pool per worker |   CPU request |  CPU limit | Memory request |   Memory limit |
| -------------------------------- | --------------: | ---------------------: | ------------: | ---------: | -------------: | -------------: |
| Light / low traffic              |               1 |                      2 |        `500m` | `1` or `2` |        `512Mi` |          `1Gi` |
| Recommended start                |               1 |                      4 | `750m` or `1` |        `2` |          `1Gi` |          `2Gi` |
| Heavy chart traffic / wider rows |               1 |                 4 to 6 |           `1` | `2` to `3` | `1Gi` to `2Gi` | `3Gi` to `4Gi` |
| Two-worker pod                   |               2 |            2 to 4 each |           `2` |        `4` |          `2Gi` |          `4Gi` |

I would **not start with 4 Uvicorn workers inside one pod**. Start with **1 worker per pod** and scale pods horizontally. Each worker process has its own Oracle pool, so this matters a lot:

```text
total Oracle sessions =
  replicas × uvicorn_workers_per_pod × ORACLE_POOL_SIZE
```

Example:

```text
6 replicas × 1 worker × pool size 4 = 24 Oracle sessions
6 replicas × 4 workers × pool size 4 = 96 Oracle sessions
```

The second configuration can accidentally overload Oracle even though the pod spec looks reasonable.

`python-oracledb` recommends connection pooling for applications that repeatedly use database connections, and pools are created at application initialization. For fetch performance, `arraysize` and `prefetchrows` tune internal fetch buffers; larger values reduce round trips but use more memory, so you should benchmark with production-like row widths. ([python-oracledb][2])

## Memory sizing formula

Use this formula after one load test:

```text
memory_limit >= idle_rss
              + active_chart_requests_per_pod × peak_memory_per_chart_request
              + 30% to 50% headroom
```

Where:

```text
active_chart_requests_per_pod =
  uvicorn_workers_per_pod × ORACLE_POOL_SIZE
```

Example for the recommended start:

```text
idle_rss                       = 200Mi
workers                        = 1
ORACLE_POOL_SIZE               = 4
active chart requests per pod  = 4
peak memory per chart request  = 80Mi

required before headroom =
  200Mi + 4 × 80Mi
= 520Mi

with 50% headroom =
  780Mi
```

So a `1Gi` memory limit may work, but I would still start with `2Gi` for production because Python memory peaks, compression, wider result rows, and temporary JSON buffers can surprise you.

For compact numeric chart payloads, 10k rows is usually not huge. The dangerous cases are:

```text
many string columns
list[dict] JSON instead of compact columnar JSON
LOBs / CLOBs / BLOBs
multiple concurrent chart requests
large gzip/brotli buffers
too many Uvicorn workers
Thick mode with large prefetch buffers
```

In Thick mode, python-oracledb documentation notes that row prefetching uses a separate buffer and an additional copy from the Oracle Client prefetch buffer, increasing memory requirements in some cases. If you use Thick mode with large `prefetchrows`, add at least **256Mi to 512Mi** to the initial memory limit and measure. ([python-oracledb][3])

After load testing, use:

```text
cpu_request =
```

```text
HPA target CPU utilization                   = 60%

cpu_request = 900m / 0.60 = 1500m
```

## Expected speedup

Approximate server-side speedup:

| Setup             | Cache hit path                       |            Typical server-side result |
| ----------------- | ------------------------------------ | ------------------------------------: |
| No cache          | Oracle + Python + JSON + compression |                              baseline |
| Redis cache       | Redis GET + return cached body       |   often **5x–50x faster** server-side |
| Nginx proxy cache | Nginx serves cached HTTP response    | often **10x–100x faster** server-side |
| Browser cache     | Browser reuses response locally      |     fastest repeat load for same user |

User-visible speedup is lower if Angular rendering is the dominant cost.

Example:

```text
Current uncached:
Oracle fetch                 350 ms
Python transform + JSON       80 ms
gzip                          40 ms
network download             120 ms
Angular parse/render         500 ms
-----------------------------------
Total                       1090 ms
```

With Nginx cache hit:

```text
Nginx cache read/send         10 ms
network download             120 ms
Angular parse/render         500 ms
-----------------------------------
Total                        630 ms
```

That is only **1.7x faster end-to-end**, even though the backend/DB part became roughly **47x faster**.

If Oracle currently takes 1–3 seconds, cache hits will feel dramatically faster. If Oracle is already 50–100 ms and the chart render takes 800 ms, caching will mostly reduce backend load rather than visibly transform the UI.

## My recommendation

For this workload, I would use this order:

```text
1. Nginx / ingress HTTP caching for whole GET responses
2. Browser caching with Cache-Control / ETag
3. Redis only when authorization, tenant logic, or invalidation is too complex for Nginx
4. Optional: pre-generate chart JSON after the RDBMS refresh
```

The best simple architecture is:

```text
Oracle 19c
  -> backend builds compact chart JSON
  -> Nginx caches the full HTTP response
  -> Angular receives cached chart payload
```

Nginx is very well suited when the exact same URL can return the same response. It can cache proxied responses and avoid calling the backend for repeated requests; its `proxy_cache_key` controls how cache entries are keyed, and `proxy_cache_lock` can ensure only one request populates a missing cache item while others wait. ([NGINX Documentation][1])

## Nginx vs Redis

### Use Nginx cache when

The chart endpoint is a normal `GET`, for example:

```text
/api/chart-data?tenant_id=123&from=2026-05-27T00:00:00Z&to=2026-05-27T23:59:59Z&metric=sales
```

and the response is identical for the same URL.

Nginx is probably better than Redis here because:

```text
- Python is not involved on cache hits
- Oracle is not involved on cache hits
- JSON serialization is not repeated
- compression can be cached
- fewer moving parts in application code
```

### Use Redis when

Use Redis when the cache key must include application-level concepts that Nginx should not decide:

```text
tenant permissions
user entitlements
chart definition version
data refresh version
feature flags
security filters
complex invalidation
```

Redis is also safer when the endpoint is authenticated and different users can see different subsets of the same tenant data. Redis supports TTL-based cache expiration, and Redis `TTL`/`EXPIRE` provide key lifetime control; `SET ... NX EX ...` is also commonly used to implement a simple lock to prevent multiple pods from rebuilding the same cache entry at once. ([Redis][2])

---

## Very important security point

Do **not** blindly put authenticated chart APIs behind a shared Nginx cache.

Bad cache key:

```text
/api/chart-data?tenant_id=123&from=...&to=...
```

Potentially safer cache key:

```text
tenant_id
+ chart_id
+ from/to
+ metric list
+ data_refresh_version
+ permission_scope_version
+ response encoding
```

If user A and user B can see different data for the same tenant/chart/date range, shared Nginx caching can leak data unless the cache key includes the correct authorization dimension. In that case, use Redis inside the backend **after** authorization has been checked.

---

## Best option if the data updates hourly/daily: versioned cache keys

TTL alone is okay. Versioned keys are better.

Instead of:

```text
chart:tenant=123:from=2026-05-27:to=2026-05-28
```

use:

```text
chart:v4:tenant=123:from=2026-05-27:to=2026-05-28:refresh=202605270900
```

When the RDBMS refresh completes, update a small `refresh_version` value. New requests use the new cache key. Old cached entries expire naturally.

This avoids the annoying case where the database refreshed at 09:05 but a `TTL=1h` cache still serves the 08:00 data until 10:00.

---

## Suggested TTL values

For hourly updates:

```text
Cache TTL:              50-60 minutes
Stale allowed:           2-10 minutes
Redis lock timeout:     15-60 seconds
Browser max-age:         5-15 minutes, or longer if versioned URLs are used
```

For daily updates:

```text
Cache TTL:              12-24 hours
Stale allowed:           10-60 minutes
Redis lock timeout:      30-120 seconds
Browser max-age:         30 minutes to several hours
```

If the chart can tolerate slightly stale data, Nginx can serve stale cached content while an update is happening. Nginx has `proxy_cache_use_stale`, `proxy_cache_background_update`, and `proxy_cache_lock` patterns for avoiding cache stampedes and avoiding many simultaneous backend calls on expiration. ([nginx][3])

## Nginx proxy cache example

This is the kind of Nginx config I would put in front of the backend.

```nginx
proxy_cache_path /var/cache/nginx/chart-api
    levels=1:2
    keys_zone=chart_api_cache:100m
    max_size=10g
    inactive=26h
    use_temp_path=off;

upstream chart_backend {
    server chart-api-service:8080;
    keepalive 64;
}

server {
    listen 8080;

    location /api/chart-data {
        proxy_pass http://chart_backend;

        proxy_http_version 1.1;
        proxy_set_header Connection "";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_cache chart_api_cache;

        # Be careful: $args is order-sensitive.
        # /chart?a=1&b=2 and /chart?b=2&a=1 can become different cache entries.
        proxy_cache_key "$scheme|$host|$uri|$args|$http_accept_encoding";

        proxy_cache_methods GET HEAD;
        proxy_cache_valid 200 60m;

        proxy_cache_lock on;
        proxy_cache_lock_timeout 10s;

        proxy_cache_use_stale updating error timeout http_500 http_502 http_503 http_504;
        proxy_cache_background_update on;

        add_header X-Cache-Status $upstream_cache_status always;
        add_header Cache-Control "public, max-age=300, stale-while-revalidate=60" always;
    }
}
```

Nginx gzip can reduce transmitted size by half or more according to the Nginx module documentation, but compression alone does not avoid Oracle or Python work. It mostly helps transfer time and client download time. ([nginx][4])

Add gzip:

```nginx
gzip on;
gzip_min_length 1024;
gzip_comp_level 4;
gzip_types application/json text/plain text/css application/javascript;
gzip_vary on;
```

For chart JSON, `gzip_comp_level 4` is a good starting point. Higher levels usually cost more CPU for diminishing returns.

## Redis cache example

Redis is best when the backend must check permissions first.

Install:

```text
redis[hiredis]
```

Example using cached **gzip bytes** for fast repeated responses:

```python
import gzip
import hashlib
import os
import time
import uuid
from typing import Any

import orjson
import redis
from fastapi import FastAPI, HTTPException, Request, Response


redis_client = redis.Redis.from_url(
    os.environ["REDIS_URL"],
    decode_responses=False,
    socket_connect_timeout=1.0,
    socket_timeout=2.0,
)


def canonical_chart_cache_key(
    *,
    tenant_id: int,
    chart_id: str,
    from_ts: str,
    to_ts: str,
    refresh_version: str,
    permission_scope: str,
) -> str:
    raw = {
        "tenant_id": tenant_id,
        "chart_id": chart_id,
        "from_ts": from_ts,
        "to_ts": to_ts,
        "refresh_version": refresh_version,
        "permission_scope": permission_scope,
        "schema": "chart-payload-v4",
    }

    encoded = orjson.dumps(raw, option=orjson.OPT_SORT_KEYS)
    digest = hashlib.sha256(encoded).hexdigest()

    return f"chart-api:gzip:{digest}"


def accepts_gzip(request: Request) -> bool:
    return "gzip" in request.headers.get("accept-encoding", "").lower()


@app.get("/api/chart-data")
def get_chart_data(
    request: Request,
    tenant_id: int,
    chart_id: str,
    from_ts: str,
    to_ts: str,
) -> Response:
    # 1. Authorize first.
    # permission_scope must represent what this user is allowed to see.
    permission_scope = authorize_and_get_scope(request, tenant_id, chart_id)

    # 2. Get refresh version.
    # Prefer Redis/config/control table populated by the ETL job.
    refresh_version = get_current_refresh_version(chart_id, tenant_id)

    cache_key = canonical_chart_cache_key(
        tenant_id=tenant_id,
        chart_id=chart_id,
        from_ts=from_ts,
        to_ts=to_ts,
        refresh_version=refresh_version,
        permission_scope=permission_scope,
    )

    ttl_seconds = 3600

    # 3. Serve cached gzip body when possible.
    if accepts_gzip(request):
        cached = redis_client.get(cache_key)
        if cached is not None:
            return Response(
                content=cached,
                media_type="application/json",
                headers={
                    "Content-Encoding": "gzip",
                    "Vary": "Accept-Encoding",
                    "Cache-Control": "private, max-age=300",
                    "X-Cache": "HIT",
                    "X-Data-Refresh-Version": refresh_version,
                },
            )

    # 4. Prevent cache stampede.
    lock_key = cache_key + ":lock"
    token = str(uuid.uuid4())
    got_lock = redis_client.set(lock_key, token.encode(), nx=True, ex=60)

    if not got_lock:
        # Another pod is building the same cache entry.
        # Wait briefly for it rather than hammering Oracle.
        deadline = time.monotonic() + 3.0

        while time.monotonic() < deadline:
            time.sleep(0.05)
            cached = redis_client.get(cache_key)
            if cached is not None and accepts_gzip(request):
                return Response(
                    content=cached,
                    media_type="application/json",
                    headers={
                        "Content-Encoding": "gzip",
                        "Vary": "Accept-Encoding",
                        "Cache-Control": "private, max-age=300",
                        "X-Cache": "HIT-AFTER-WAIT",
                        "X-Data-Refresh-Version": refresh_version,
                    },
                )

        # Fallback: build without owning the lock.
        # This protects latency if the lock holder died or is slow.

    try:
        # 5. Your existing fast Oracle query.
        payload: dict[str, Any] = build_chart_payload_from_oracle(
            tenant_id=tenant_id,
            chart_id=chart_id,
            from_ts=from_ts,
            to_ts=to_ts,
            permission_scope=permission_scope,
        )

        json_body = orjson.dumps(payload)
        gzip_body = gzip.compress(json_body, compresslevel=4)

        redis_client.setex(cache_key, ttl_seconds, gzip_body)

        if accepts_gzip(request):
            return Response(
                content=gzip_body,
                media_type="application/json",
                headers={
                    "Content-Encoding": "gzip",
                    "Vary": "Accept-Encoding",
                    "Cache-Control": "private, max-age=300",
                    "X-Cache": "MISS",
                    "X-Data-Refresh-Version": refresh_version,
                },
            )

        return Response(
            content=json_body,
            media_type="application/json",
            headers={
                "Vary": "Accept-Encoding",
                "Cache-Control": "private, max-age=300",
                "X-Cache": "MISS",
                "X-Data-Refresh-Version": refresh_version,
            },
        )

    finally:
        # Safe unlock should compare token before delete.
        # For brevity, this example omits the Lua compare-and-delete script.
        pass
```

In real production code, release the Redis lock with a Lua compare-and-delete script so one worker does not delete a lock created later by another worker. Redis’ own SET documentation describes using a random token and deleting only when the token matches. ([Redis][5])

## The fastest design: pre-generate after refresh

Since the data changes only hourly/daily, the fastest architecture is often:

```text
RDBMS refresh completes
  -> job generates chart JSON/gzip once
  -> stores it in Redis / object storage / Nginx static volume
  -> Angular requests already-built chart file
```

That avoids the first user after refresh paying the Oracle cost.

For example:

```text
/chart-cache/tenant-123/chart-sales/refresh-202605270900.json.gz
```

Then Nginx can serve it almost like a static asset.

This is ideal when:

```text
the number of chart combinations is known
the same chart is opened by many users
the data freshness boundary is tied to ETL refresh completion
```

It is not ideal when users can choose arbitrary filters that create thousands of unique combinations.

Then runtime becomes:

```text
Angular -> backend/Nginx -> prebuilt JSON/gzip -> Angular chart
```

instead of:

```text
Angular -> backend -> Oracle -> transform -> JSON -> gzip -> Angular chart
```

For your use case, this is usually better than adding Redis as a traditional request-time cache.

# Best architecture choices

## Option 1 — Best if chart combinations are known

Use a **post-refresh warm job** that pre-generates the exact chart responses.

Example:

```text
daily/hourly ETL finishes
  -> calls /internal/warm-charts?refresh_version=202605271000
  -> backend generates:
       tenant 1 / chart A / default date range
       tenant 1 / chart B / default date range
       tenant 2 / chart A / default date range
  -> stores compressed JSON
```

Then the user-facing endpoint simply does:

```text
read prebuilt payload -> return response
```

This gives fast first use.

You can store the prebuilt payload in:

```text
Redis
object storage
a database table
a mounted/static file served by Nginx
```

For few users, I would prefer:

```text
prebuilt payload in Redis or object storage
```

Redis is fastest, but object storage or a DB table is more durable across Redis restart/eviction.

---

## Option 2 — Best if users can choose many filters

If users can choose arbitrary date ranges, metrics, regions, filters, etc., you may not be able to prebuild every possible chart.

Then use:

```text
Oracle materialized view / summary table
  -> backend still queries Oracle
  -> query reads pre-aggregated chart-ready data
```

Oracle materialized views are designed for precomputed query results and can be refreshed after changes to base tables. Oracle 19c supports complete refresh, fast/incremental refresh, partition change tracking, and on-demand refresh through `DBMS_MVIEW`, though fast refresh has design requirements such as materialized view logs for many cases. ([Oracle Docs][1])

This makes the **first request fast** without requiring Redis to already contain every possible key.

A common pattern is:

```sql
create table chart_points_hourly (
    tenant_id       number not null,
    chart_id        varchar2(100) not null,
    bucket_start    timestamp not null,
    metric_a_avg    number,
    metric_a_min    number,
    metric_a_max    number,
    metric_b_avg    number,
    sample_count    number,
    refresh_version varchar2(30) not null,
    constraint chart_points_hourly_pk
      primary key (tenant_id, chart_id, bucket_start, refresh_version)
);
```

Then the API queries a much smaller table:

```sql
select bucket_start, metric_a_avg, metric_a_min, metric_a_max, metric_b_avg
from   chart_points_hourly
where  tenant_id = :tenant_id
and    chart_id = :chart_id
and    refresh_version = :refresh_version
and    bucket_start >= :from_ts
and    bucket_start <  :to_ts
order  by bucket_start
```

This is often the best solution for chart APIs.

---

## Option 3 — Nginx cache with proactive warming

Nginx can work well, but **only if you warm it**.

Nginx proxy caching can cache upstream responses, and `proxy_cache_lock` can prevent multiple concurrent cache misses from all hitting the backend for the same cache key. ([nginx][2]) Nginx can also serve stale cached responses while an expired item is being refreshed using `proxy_cache_use_stale updating` and `proxy_cache_background_update`. ([nginx][2])

But with infrequent use, watch out for this:

```nginx
inactive=60m
```

If nobody uses the chart for more than 60 minutes, Nginx may remove it from cache even if the logical TTL has not expired.

For your case, use a longer inactive period:

```nginx
proxy_cache_path /var/cache/nginx/chart-api
    levels=1:2
    keys_zone=chart_api_cache:100m
    max_size=5g
    inactive=2d
    use_temp_path=off;
```

Then after the data refresh, run a warm job that calls the important chart URLs:

```bash
curl -s -H "Accept-Encoding: gzip" \
  "https://your-host/api/chart-data?tenant_id=1&chart_id=sales&range=default" \
  -o /dev/null
```

That makes the first real user hit Nginx cache.

# Redis vs Nginx for your low-usage case

## Redis is useful if

```text
you want the backend to control authorization
you want versioned cache keys
you want to store prebuilt payloads directly
you want to warm keys after refresh
you do not want to depend on URL-level cache behavior
```

Redis supports key expiration via `EXPIRE`, where a key is automatically deleted after its timeout. ([Redis][3]) But for your case, I would avoid relying only on TTL. Use **versioned keys** instead.

Example:

```text
chart:v5:tenant=123:chart=sales:range=default:refresh=202605271000
```

When new data is loaded, the refresh version changes:

```text
chart:v5:tenant=123:chart=sales:range=default:refresh=202605271100
```

Old keys can expire later.

## Nginx is useful if

```text
the same URL always returns the same response
authorization is simple or not user-specific
you want cache hits to avoid Python entirely
you want to cache compressed HTTP responses
```

But again: **Nginx alone does not make first use fast unless warmed.**

```python
    *,
    tenant_id: int,
    chart_id: str,
    range_name: str,
    refresh_version: str,

    """
    Your existing optimized Oracle query goes here.

    Return chart-shaped payload, not table-shaped rows:
      {
        "x": [...],
        "series": [
          {"name": "metricA", "data": [...]}
        ]
      }
    """
    ...

    """
    Query Oracle chart_refresh_state, or read from config/Redis if your ETL
    stores the latest version there.
    """
    ...


@router.post("/internal/warm-charts")
def warm_charts() -> dict[str, Any]:
    refresh_version = get_current_refresh_version("daily_sales")

    warmed = []
    failed = []

    for item in CHARTS_TO_WARM:
        key = cache_key(
            tenant_id=item["tenant_id"],
            chart_id=item["chart_id"],
            range_name=item["range"],
            refresh_version=refresh_version,
        )

        try:
            payload = build_chart_payload_from_oracle(
                tenant_id=item["tenant_id"],
                chart_id=item["chart_id"],
                range_name=item["range"],
                refresh_version=refresh_version,
            )

            json_body = orjson.dumps(payload)
            gzip_body = gzip.compress(json_body, compresslevel=4)

            # Long TTL is okay because refresh_version prevents stale reuse.
            # Old versions expire naturally.
            redis_client.setex(key, 3 * 24 * 3600, gzip_body)

            warmed.append(
                {
                    "key": key,
                    "bytes_gzip": len(gzip_body),
                    "points": payload.get("count"),
                }
            )

        except Exception as exc:
            failed.append(
                {
                    "tenant_id": item["tenant_id"],
                    "chart_id": item["chart_id"],
                    "range": item["range"],
                    "error": str(exc),
                }
            )

    if failed:
        raise HTTPException(
            status_code=500,
            detail={"warmed": warmed, "failed": failed},
        )

    return {
        "refresh_version": refresh_version,
        "warmed_count": len(warmed),
        "warmed": warmed,
    }
```

# Even simpler: prebuilt payload table in Oracle

If you do not want Redis operationally, store the final chart JSON/gzip in Oracle.

```sql
create table chart_payload_cache (
```

```text
query raw/summary data
```

```text
select payload_blob
```

This still hits Oracle, but it avoids:

```text
30M-row table access
large query planning/execution
Python row transformation
JSON serialization
gzip compression
```

It is not as fast as Redis, but it is durable and simple.

For few users, this can be a very good tradeoff.

Prefer:

# Expected speed difference

For first use:

| Design                           |                            First user after data refresh |
| -------------------------------- | -------------------------------------------------------: |
| No cache                         |                                                 baseline |
| Lazy Redis cache                 |                                 same as baseline on miss |
| Lazy Nginx cache                 |                                 same as baseline on miss |
| Warmed Redis payload             |                          often near Redis + network time |
| Warmed Nginx response            |                          often near static-response time |
| Oracle summary/materialized view | still queries DB, but usually much faster than raw table |
| Prebuilt payload in Oracle table |       one small BLOB read, no chart query/JSON/gzip work |

The key point:

```text
Lazy cache improves the second request.
Precompute/warm improves the first request.
```

# My concrete recommendation

For your exact situation, I would implement this:

```text
1. Keep backend minReplicas = 1 or 2.
2. Create a refresh_version value after every RDBMS data update.
3. After refresh, run a warm job.
4. Warm job builds compact chart JSON and gzip-compresses it.
5. Store it in Redis with a long TTL, keyed by refresh_version.
6. User endpoint serves Redis payload first.
7. Fallback to Oracle only if the prebuilt key is missing.
```

If you do not want Redis, store the prebuilt gzip JSON in an Oracle cache table or object storage. For low usage, durability may matter more than shaving the last few milliseconds.

# Backend: build ApexCharts-ready payload

```python
import datetime as dt
import decimal
import gzip
import os
from typing import Any

import oracledb
import orjson
import redis
from fastapi import FastAPI, HTTPException, Request, Response


app = FastAPI()

POOL: oracledb.ConnectionPool | None = None

redis_client = redis.Redis.from_url(
    os.environ["REDIS_URL"],
    decode_responses=False,
    socket_connect_timeout=1.0,
    socket_timeout=2.0,
)


SQL_APEX_CHART = """
select
       event_ts_utc,
       metric_a,
       metric_b
from   my_schema.my_chart_table
where  tenant_id = :tenant_id
and    event_ts_utc >= :from_ts
and    event_ts_utc <  :to_ts
order  by event_ts_utc
fetch next :limit rows only
"""


def to_epoch_ms(value: dt.datetime) -> int:
    if value.tzinfo is None:
        value = value.replace(tzinfo=dt.timezone.utc)
    else:
        value = value.astimezone(dt.timezone.utc)

    return int(value.timestamp() * 1000)


def chart_number(value: Any) -> float | int | None:
    if value is None:
        return None

    if isinstance(value, int):
        return value

    if isinstance(value, decimal.Decimal):
        # For charts, float is usually fine.
        # For financial values, consider scaling in SQL and returning integers.
        return float(value)

    return float(value)


def build_apex_payload_from_oracle(
    *,
    tenant_id: int,
    from_ts: dt.datetime,
    to_ts: dt.datetime,
    refresh_version: str,
    limit: int = 10_000,
) -> dict[str, Any]:
    if POOL is None:
        raise RuntimeError("Oracle pool is not initialized")

    metric_a_data: list[list[float | int | None]] = []
    metric_b_data: list[list[float | int | None]] = []

    params = {
        "tenant_id": tenant_id,
        "from_ts": from_ts,
        "to_ts": to_ts,
        "limit": limit,
    }

    with POOL.acquire() as conn:
        with conn.cursor() as cur:
            # For fixed max 10k rows, this is usually a good starting point.
            cur.arraysize = limit
            cur.prefetchrows = limit + 1

            cur.execute(SQL_APEX_CHART, params)

            for event_ts_utc, metric_a, metric_b in cur:
                ts_ms = to_epoch_ms(event_ts_utc)

                metric_a_data.append([ts_ms, chart_number(metric_a)])
                metric_b_data.append([ts_ms, chart_number(metric_b)])

    return {
        "refreshVersion": refresh_version,
        "count": len(metric_a_data),
        "series": [
            {
                "name": "Metric A",
                "data": metric_a_data,
            },
            {
                "name": "Metric B",
                "data": metric_b_data,
            },
        ],
        "xaxis": {
            "type": "datetime",
            "min": to_epoch_ms(from_ts),
            "max": to_epoch_ms(to_ts),
        },
    }
```

For one or two series, `[[timestampMs, value], ...]` is the format I would use. If you have many series sharing exactly the same timestamps, you can also test a smaller payload using one shared `xaxis.categories` array and `series[].data` as y-only arrays, because ApexCharts supports `xaxis.categories` and `xaxis.type` values including `datetime`; but timestamp pairs are the most reliable across chart types and versions. ([ApexCharts.js][2])

```python
                "X-Data-Refresh-Version": refresh_version,
            },
        )

    return Response(
        content=json_body,
        media_type="application/json",
        headers={
            "Vary": "Accept-Encoding",
            "Cache-Control": "private, max-age=300",
            "ETag": f'"{key}"',
            "X-Cache": "MISS-REBUILT",
            "X-Data-Refresh-Version": refresh_version,
        },
    )
```

With this design, the first real user after refresh should not hit the 30M-row table at all.

# Angular / ng-apexcharts side

The `ng-apexcharts` wrapper expects at least `series` and `chart` inputs, and exposes inputs such as `xaxis`, `yaxis`, `dataLabels`, `markers`, `stroke`, `tooltip`, etc. ([GitHub][3])

```ts
import { Component, ChangeDetectionStrategy } from '@angular/core';
import {
  ApexAxisChartSeries,
  ApexChart,
  ApexXAxis,
  ApexDataLabels,
  ApexMarkers,
  ApexStroke,
  ApexTooltip
} from 'ng-apexcharts';

interface ApexChartPayload {
  refreshVersion: string;
  count: number;
  series: ApexAxisChartSeries;
  xaxis: ApexXAxis;
}

@Component({
  selector: 'app-my-chart',
  template: `
    <apx-chart
      [series]="series"
      [chart]="chart"
      [xaxis]="xaxis"
      [dataLabels]="dataLabels"
      [markers]="markers"
      [stroke]="stroke"
      [tooltip]="tooltip">
    </apx-chart>
  `,
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class MyChartComponent {
  series: ApexAxisChartSeries = [];

  chart: ApexChart = {
    id: 'main-chart',
    type: 'line',
    height: 420,

    animations: {
      enabled: false
    },

    zoom: {
      enabled: true,
      type: 'x',
      autoScaleYaxis: true
    },

    toolbar: {
      show: true,
      autoSelected: 'zoom'
    },

    // Use only if your ApexCharts version supports it.
    // Current ApexCharts docs show dataReducer with LTTB.
    dataReducer: {
      enabled: true,
      algorithm: 'lttb',
      threshold: 2000,
      targetPoints: 1200
    } as any
  };

  xaxis: ApexXAxis = {
    type: 'datetime'
  };

  dataLabels: ApexDataLabels = {
    enabled: false
  };

  markers: ApexMarkers = {
    size: 0,
    strokeWidth: 0
  };

  stroke: ApexStroke = {
    width: 2,
    curve: 'straight'
  };

  tooltip: ApexTooltip = {
    shared: true,
    intersect: false
  };

  loadChart(): void {
    this.http.get<ApexChartPayload>('/api/apex-chart', {
      params: {
        tenant_id: '123',
        chart_id: 'sales',
        from_ts: '2026-05-31T00:00:00Z',
        to_ts: '2026-06-01T00:00:00Z'
      }
    }).subscribe(payload => {
      this.series = payload.series;
      this.xaxis = {
        ...this.xaxis,
        ...payload.xaxis
      };
    });
  }
}
```

A few Apex-specific notes matter for 10k points:

```ts
animations: { enabled: false }
```

ApexCharts animations are enabled by default and include initial/data-update animation; disabling them usually helps large chart first render. ([ApexCharts.js][4])

```ts
dataLabels: { enabled: false }
```

ApexCharts data labels are enabled by default in the documented option reference, and drawing labels for thousands of points is expensive and visually noisy. ([ApexCharts.js][5])

```ts
markers: { size: 0, strokeWidth: 0 }
```

Markers default to size `0` in the current docs, but I would still set this explicitly so future option changes or shared config do not accidentally draw 10k SVG markers. ([ApexCharts.js][6])

```ts
dataReducer: {
  enabled: true,
  algorithm: 'lttb',
  threshold: 2000,
  targetPoints: 1200
}
```

Current ApexCharts docs include `chart.dataReducer`, which downsamples large datasets before rendering using LTTB and is off by default. This is useful when the chart is visually displayed in maybe 800–1600 horizontal pixels but the backend sends 10k points. ([ApexCharts.js][4])

# Important version check

`dataReducer` appears in the current ApexCharts docs. If your app uses an older ApexCharts/ng-apexcharts combination, it may not exist. The current `ng-apexcharts` README shows recent 2.x versions paired with ApexCharts 5.x, while older Angular versions map to older ApexCharts ranges. ([GitHub][3])

So:

```text
If you are on ApexCharts 5.x:
  try chart.dataReducer.

If you are on ApexCharts 3.x/4.x:
  do downsampling in Oracle/Python instead, or upgrade after testing.
```

# My concrete recommendation for your setup

Given all your constraints:

```text
Oracle data changes hourly/daily
few users
infrequent usage
first use must be fast
Angular uses ApexCharts
max around 10k rows/points
```

I would implement:

```text
1. After each RDBMS refresh, run a warm job.
2. Warm job queries Oracle once.
3. Python builds ApexCharts-native series:
     series: [{ name, data: [[epochMs, value], ...] }]
4. Python gzip-compresses that exact JSON.
5. Store it in Redis, object storage, or an Oracle payload-cache table.
6. Angular receives the already-built Apex payload.
7. ApexCharts renders with animations off, dataLabels off, markers off.
8. Use dataReducer or server-side downsampling if browser rendering is still slow.
```

For this situation, **Redis/Nginx as lazy caches are secondary**. The real win is **prebuilt ApexCharts payloads**. That makes the first user fast because the expensive Oracle query and JSON shaping already happened before the user opened the chart.
