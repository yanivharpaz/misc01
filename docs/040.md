Mostly **no, not by itself**.

`ALTER TABLE xx NOLOGGING` only changes the table’s logging attribute. It **does not make normal inserts/updates/deletes stop generating redo**.

The key rule is:

```sql
alter table xx nologging;
```

helps only when the load uses a **direct-path operation**, for example:

```sql
insert /*+ append */ into xx
select ...
from source_table;

commit;
```

Oracle’s docs say that with `NOLOGGING`, **conventional inserts are still logged**, while **direct-path inserts are not logged** for the data portion, assuming the database or tablespace is not in `FORCE LOGGING`. ([Oracle Docs][1])

So for a staging table:

```sql
alter table stg_x nologging;

truncate table stg_x;

insert /*+ append */ into stg_x
select ...
from ...;

commit;
```

That is the usual pattern if the staging data is disposable/reloadable.

Important caveats:

1. **Regular inserts still generate redo**

   This:

   ```sql
   insert into stg_x values (...);
   ```

   or a normal application/JDBC batch insert will still generate normal redo. Oracle documents that conventional `INSERT` always generates redo and undo for data and metadata, regardless of the table’s logging setting. ([Oracle Docs][2])

2. **`UPDATE` and `DELETE` still generate redo**

   `NOLOGGING` is mainly useful for bulk load-style operations, not ongoing row-by-row DML.

3. **`FORCE LOGGING` overrides it**

   If the database or tablespace is in `FORCE LOGGING`, Oracle ignores the table’s `NOLOGGING` setting. This is common in Data Guard / standby environments. ([Oracle Docs][1])

   Check:

   ```sql
   select force_logging from v$database;

   select tablespace_name, force_logging
   from dba_tablespaces
   where tablespace_name = 'YOUR_TABLESPACE';
   ```

4. **It still produces some redo**

   Even with direct-path `INSERT` into a `NOLOGGING` table, Oracle still writes redo for metadata/dictionary changes and extent invalidation. So it is “minimal redo,” not literally zero redo. ([Oracle Docs][1])

5. **Indexes can still be a big redo source**

   If the staging table has indexes, maintaining them during load can generate redo. For pure staging tables, often the fastest pattern is:

   ```sql
   truncate table stg_x;

   -- optionally drop/disable/rebuild indexes depending on your process

   insert /*+ append */ into stg_x
   select ...
   from ...;

   commit;
   ```

6. **Recovery risk**

   `NOLOGGING` operations are not fully recoverable from redo. Oracle notes that media recovery from a backup taken before a `NOLOGGING` operation does not recreate the object’s data; for important objects, take a backup after the `NOLOGGING` load. ([Oracle Docs][1])

For a disposable staging table, `NOLOGGING` plus `INSERT /*+ APPEND */` is usually the right idea. For normal row-by-row staging inserts, `ALTER TABLE xx NOLOGGING` alone will not materially reduce redo.
