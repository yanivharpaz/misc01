Working in an air-gapped environment with non-vision coding agents (Roo Code and OpenCode) alongside a separate, isolated Vision LLM chat presents a classic context-decoupling problem.

Because your coding agents cannot directly inspect UI screenshots or wireframes, you must convert visual data into deterministic, text-based specifications that non-vision models excel at parsing.

1. The "Vision-to-Structured-Text" (V2ST) Pipeline
Instead of attempting to describe visual layouts in conversational English to Roo Code, use your network’s standalone Vision Chat LLM as a Visual Parser & Compiler.

The V2ST Parsing Prompt
When uploading a screenshot, wireframe, or UI mockup to the Vision Chat LLM, request a structural spec rather than code:

"Deconstruct this UI image into a strict structural Markdown specification. Do not write implementation code. Output the following:

Component Hierarchy Tree: (Parent-child relationships using indented markdown).

Layout Engine Requirements: (For each container, specify: Flex direction vs. Grid columns, alignment, overflow behaviors, gap/padding estimates).

Design Tokens: (Color palette in HEX/HSL, typography scale, border radiuses, box-shadows).

State Hooks Needed: (Identify interactive elements, hover states, mobile collapse points, dynamic list containers)."*

Integrating with Roo Code
Copy the resulting spec into a markdown file in your repository (e.g., .roo/specs/ui-target.md).

In Roo Code, reference this spec using context mentions:

@.roo/specs/ui-target.md Implement the user settings form component based on this specification using TypeScript and our design tokens.

2. Visual Debugging Without In-Context Vision
When a layout breaks visually (e.g., unwanted line wraps, bad alignment, clipping), coding LLMs fail if you only provide vague text like "the button is shifted down." Use DevTools data exports to give the text model exact spatial data.

Method A: DevTools DOM + Computed Styles (Primary Strategy)
Text-based LLMs process computed CSS properties with extreme accuracy because layout engines are mathematical constraint solvers.

Inspect the broken element in Browser DevTools.

Copy the Outer HTML of the parent container and child elements.

In the Console, extract the problematic computed styles of the parent and target child:

JavaScript
// Quick console snippet to dump key box-model properties
const el = $0; // selected element in DevTools
const s = getComputedStyle(el);
console.log({
  display: s.display, flexDirection: s.flexDirection, flexWrap: s.flexWrap,
  justifyContent: s.justifyContent, alignItems: s.alignItems,
  width: s.width, height: s.height, boxSizing: s.boxSizing,
  position: s.position, overflow: s.overflow
});
Pass the HTML + Computed Styles object directly to Roo Code.

Method B: Vision-Assisted Defect Diagnosis (For Complex Visual Artifacts)
If you cannot identify why a layout is breaking visually:

Take a screenshot of the broken rendering in your browser.

Upload it to the standalone Vision LLM with this prompt:

"Analyze this rendering defect. Identify the exact CSS box-model conflict (e.g., flex basis calculation error, stacking context collision, overflow clipping) and state which DOM node is misbehaving."

Copy the Vision LLM’s technical diagnosis and feed it to Roo Code along with the relevant source file.

3. Roo Code Workspace Rules (.roo/rules/)
Because the coding LLMs cannot "see" the output, you must constrain their generation using strict system rules so they don't produce invalid layouts or inline CSS hacks.

Set up workspace rules in your repository root under .roo/rules/:

Markdown
# Frontend Architecture & Styling Rules

## Layout Standards
- Use Flexbox for 1D layout components and CSS Grid for 2D page-level layouts.
- NEVER use absolute positioning (`position: absolute`) for standard document flow positioning.
- All layout containers MUST explicitly define overflow behavior (`overflow: hidden`, `overflow-y: auto`, etc.).

## CSS & Styling Constraints
- Rely exclusively on utility classes (Tailwind) or scoped CSS Modules.
- Do not generate arbitrary inline styles (`style={{ ... }}`).
- Use established spacing variables/tokens (`gap-4`, `p-6`) instead of hardcoded pixel values.

## Component Contract
- Keep UI components small, stateless, and focused strictly on presentation.
- Pass state down via props; lift event handlers up.

Operating across an air-gap with an isolated Vision Web Chat on one side and OpenCode in VS Code on the other means you are acting as the "Context Router."

To make this workflow effortless, treating the Vision Web Chat as a Visual OCR & Layout Constraint Extractor—rather than a code generator—is key. The Web Chat lacks knowledge of your specific codebase, Angular setup, or backend models, while OpenCode lacks eyes.

Here is a complete operational protocol along with ready-to-use prompt pairs.

The "Context-Router" Core Rules
Never ask the Web Chat for complete code: It doesn't know your file structure, Angular 19 Signal setup, or styling variables. Asking it for code yields generic, hard-to-integrate snippets.

Force structured output (Markdown/YAML): Ask the Web Chat to format its analysis as structured text. This makes it trivial to copy-paste into VS Code or save as a .md file for OpenCode to digest.

Use the Spec-File Workflow: For complex features, save the Web Chat's output directly into a temporary file in your workspace (e.g., .opencode/ui-spec.md). Then in OpenCode, reference it using @.opencode/ui-spec.md.

Playbook 1: New UI Component / Wireframe Implementation
Use this when you have a screenshot of a design, wireframe, or another application UI that you need to build in Angular.

Step 1: Prompt for the Vision Web Chat
Upload the screenshot/mockup and run this prompt:

Vision Chat Prompt:

Plaintext
Deconstruct this UI image into a strict Markdown specification for a developer. Do not generate full application code.

Output the following sections:
1. Component Architecture:
   - Break down the layout into a hierarchical component tree (Parent -> Children -> Atomic elements).
2. Layout & Spacing Engine:
   - Primary container layout strategy (CSS Grid vs Flexbox).
   - Alignment, flex-direction, gap, padding, and dynamic wrapping behavior.
3. State Requirements:
   - List all interactive elements (buttons, inputs, toggles, dropdowns) and the implicit reactive state each requires (e.g., active, disabled, dynamic data bindings).
4. Visual Tokens & Styling:
   - Color palette (hex/hsl estimates), typography scale, borders, and shadows.
